Timestamp Format Options

When specifying timestamps, you can choose from the following three formats:

  1. ISO 8601 Format:
    • This format includes the full date and time, with an optional timezone indicator.
    • Examples:
      • 2026-01-01T17:00Z (UTC time)
      • 2026-01-01T18:00+01:00 (Local time offset by +01:00)
  2. Daily Format:
    • This format specifies only the date.
    • The start time is assumed to be at 00:00 on the specified date in the local timezone of the specified country or bidding zone (bzn).
    • The end timestamp is interpreted as the last minute of the specified day in the same local timezone.
    • Example:
      • 2026-01-01 (Starts at 00:00 and ends at 23:59 on January 1, 2026, local time)
  3. UNIX Timestamp:
    • This format specifies the time as the number of seconds since the Unix Epoch (January 1st, 1970, at 00:00 UTC).
    • Example:
      • 1767222000

Default Behavior for Timestamps

If an end timestamp is not explicitly provided, it is assumed to be the same as the start timestamp. For daily formats, this means that one full day will be returned. If also no start timestamp is provided, the current day in the local timezone is used.

Timestamp Semantics in Responses

All timestamps returned by the API mark the beginning of the period the value refers to. Single exception: /installed_power and /v2/installed_power, where the timestamp labels the reporting year or month and the value represents the installed power at the end of that period (or, with installation_decommission=true, the net change during the period).

Rate Limiting

Requests are limited per client IP and per endpoint (token bucket, so short bursts are allowed). The default is 2 requests per minute with a burst of 4; /signal allows 20 per minute (burst 40), /price 2 per minute (burst 2), and every /v2 endpoint inherits the limit of its v1 counterpart. In addition, the limits are adjusted dynamically to the current server load, so the effective limit can be lower during peak times.

Exceeding a limit returns HTTP 429 with a Retry-After header giving the number of seconds to wait. Clients should honour that header instead of assuming fixed limits, and cache responses on their side. For higher limits (commercial access) please contact leonhard.gandhi@ise.fraunhofer.de.

Discontinuation of endpoints

Endpoint discontinuations will be preceded by an announcement at least six months in advance, indicated by setting the "deprecated" status to true.

New in release v2.0 (2026-07-20)
  • New machine-readable /v2/... twin for every public endpoint (v1 endpoints remain unchanged)
  • New endpoints /v2/price_current (price of the current interval, with valid_until) and /v2/price_next_day (full day-ahead curve for tomorrow)
  • Machine-readable catalog of all v2 endpoints at GET /v2
  • LLM-friendly API self-description at /llms.txt and /llms-full.txt (llmstxt.org convention)
  • Uniform self-describing response envelope: ISO 8601 timestamps in local timezone, explicit timezone, unit, resolution/interval_minutes
  • Series identified by stable snake_case ids; row-oriented data records (timestamp + values)
  • generated_at, available_from and available_until reflect the data actually available at generation time
  • Closed enum value lists for country, bzn, production_type, forecast_type and time_step in the OpenAPI schema
